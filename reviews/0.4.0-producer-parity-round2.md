## Release gates (confirmed majors)

### G1 — The spec's new normative sentence — "legend consumers receive neutralized values, never raw arrows" — is false for `legend[].href`, which carries the raw ⟷ glyph verbatim (CONFIRMED, correctness; severity uncertain, treated as gating)

`src/index.ts:765-766` (`elided.href = w.href`, no `neutralizeArrows`), `README.md` ~106-108 (the unqualified sentence), `CHANGELOG.md` ~54 (repeats the claim).

Reproduced by execution: a record with href `https://x.test/?q=a ⟷ fake.path` yields `legend[].href` carrying the raw U+27F7 arrow verbatim, while the same string is neutralized to `<->` in the caption field of the same legend entry — the choke point demonstrably misses this path, defeating any "intentionally exempt" reading. In the DOM-producer threat model this remediation exists for, a legend consumer implementing the sentence as written (splitting at the last arrow across legend values, or forwarding legend strings into a caption run trusting "never raw arrows") mis-parses an attacker-controlled URL into shown-value + fake path, or reintroduces the tofu glyph the grammar's first law bans. haltija#45 cites this spec as its implementation guide, so the false sentence is being implemented against right now. No test pins legend-href behavior either way.

**Remediation — make code and spec agree, and note that blind neutralization is probably WRONG here**: rewriting arrows inside an href corrupts the destination, the one fact an agent acts on. Likely fix (spec-side): amend the README sentence to carve out `href` — carried verbatim as an opaque destination; it is in the never-scanned identity/name set, so no arrow in it is ever structural and consumers must never parse provenance from it — extend the same caveat to legend `flags` (copied raw when cramped), fix the CHANGELOG sentence, and pin with a test that a hostile href reaches the legend verbatim while conferring nothing. If neutralizing instead, call out the URL-corruption tradeoff explicitly. **Re-review scope**: spec-side (sentence + pinning test) → Tier 0 only; code-side → correctness + blast-radius over the remediation diff (constraint 3 applies — legend JSON is a consumed channel).

### G2 — The constraint-3 byte-stability guard is unwired, and its header falsely claims release-doctor runs it — the guard will silently not fire at the next release (CONFIRMED, blast-radius; severity uncertain, treated as gating)

`tools/byte-stability.ts:11-12` ("run it as part of the pre-tag review instead (release-doctor reports it)").

Verified: release-doctor.ts contains no byte-stability check and no repo-local-tool mechanism; the pre-release-review skill's Tier 0 never mentions the tool; `prepublishOnly` is `bun test && bun run build`; no TODO.md item or UPSTREAM.md issue tracks the wiring. So at the next tag, Tier 0 runs release-doctor, nobody runs the tool because the comment says release-doctor covers it, and incidental SVG drift for unchanged inputs ships — vendored verbatim into tosijs's committed dist/ and docs/ (constraint 2), breaking downstream snapshot consumers — exactly the damage class the prior review's follow-up ("wire into prepublishOnly or release-doctor", reviews/0.4.0-producer-parity.md:57) created this tool to prevent. The false wiring claim is worse than no claim: it converts a missing guard into a trusted one, and committing the tool with it closed that follow-up without satisfying it. Mitigating color: the tool itself works — run during verification, both fixtures byte-identical to published 0.3.0 — so the defect is purely the false claim plus absent wiring.

**Remediation**: correct the header comment now. Then wire it for real: either a package.json script (e.g. `"stability": "bun tools/byte-stability.ts"`) named as a mandatory pre-tag step in this repo's release notes, or — per file-don't-fix — the upstream seam below (release-doctor project-local preflight hook), mirrored in UPSTREAM.md. **Re-review scope**: Tier 0 only.
